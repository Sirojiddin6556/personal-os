# Incident Response Runbook

## Серьезность инцидентов
- **P0: Критический инцидент** — полная недоступность сервиса / утечка данных / коррупция базы данных (время ответа < 15 мин, эскалация CTO / Lead DevOps)
- **P1: Высокий инцидент** — основные бизнес-функции нарушены (авторизация, создание задач, отправка сообщений), обходные пути отсутствуют (время ответа < 1ч)
- **P2: Средний инцидент** — деградация некритических функций (фоновые синки, генерация второстепенных дашбордов, задержка AI рекомендаций) (время ответа < 4ч)
- **P3: Низкий инцидент** — незначительные UI/UX баги, опечатки, косметические дефекты (время ответа в рамках стандартного спринта)

## P0 Чеклист
1. Проверить Grafana дашборд (доступность, RPS, HTTP 5xx ошибки, latency P95/P99)
2. Проверить Sentry (новые unhandled exceptions, всплески ошибок за последние 15 минут)
3. Проверить `docker compose ps` (состояние контейнеров, статус `healthy` / `unhealthy`, неожиданные перезапуски)
4. `docker compose logs api --tail=100` (анализ последних логов бэкенда на наличие traceback, panic, OOM)
5. Если DB: `pg_isready` (проверка доступности пула соединений PostgreSQL, лимита max_connections и блокировок)
6. Откат или рестарт: `docker compose restart api` (в случае зависания процессов или рестарт конкретного воркера/сервиса)

## Пошаговые сценарии реагирования

### Сценарий 1: PostgreSQL недоступен или исчерпан пул соединений
1. Проверить статус контейнера: `docker compose ps postgres`
2. Проверить логи: `docker compose logs postgres --tail=100`
3. Проверить активность подключений:
   ```bash
   docker compose exec postgres psql -U personal_os -c "SELECT count(*), state FROM pg_stat_activity GROUP BY state;"
   ```
4. Если база данных зависла из-за долгоживущих блокировок:
   ```bash
   docker compose exec postgres psql -U personal_os -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle in transaction' AND state_change < current_timestamp - INTERVAL '5 minutes';"
   ```
5. В крайнем случае выполнить контролируемый перезапуск:
   ```bash
   docker compose restart postgres
   ```

### Сценарий 2: Переполнение диска или очереди Redis
1. Проверить использование диска: `df -h`
2. Проверить размер данных Redis: `docker compose exec redis redis-cli info memory`
3. Очистить неактивные временные файлы и старые Docker-образы:
   ```bash
   docker system prune -f
   ```

### Сценарий 3: Аварийное восстановление из резервной копии (Disaster Recovery)
Если произошла критическая порча данных, применить проверенный скрипт восстановления:
1. Запустить процедуру верифицированного восстановления:
   ```bash
   bash infra/scripts/restore-drill.sh
   ```
2. Подтвердить целостность данных и восстановить боевую базу данных из последнего снапшота в S3.

## Коммуникация и Post-Mortem
1. Создать инцидент-тикет в трекере с меткой `incident-p0`.
2. Оповестить команду в канале `#incidents`.
3. После локализации проблемы провести Blameless Post-Mortem в течение 48 часов с описанием первопричины (Root Cause), хронологии (Timeline) и корректирующих мер (Action Items).
