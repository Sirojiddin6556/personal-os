### 1.2 Детализация эпиков и фичей

#### EPIC-01: Identity & Platform
- **Приоритет:** P0 | **Спринты:** S1–S2 | **MVP:** Да | **Total SP:** 18
- **Цель:** Обеспечить безопасную аутентификацию пользователей, поддержку изоляции данных рабочих пространств (multi-tenancy) и базовую платформенную инфраструктуру для агрегации данных.
- **Фичи:**
  - **FEAT-01-1: Multi-tenant Workspace & Auth API (OIDC / OAuth2 / JWT)**
    - *Описание:* Регистрация, вход через OIDC/Google OAuth и Email/Password, выдача short-lived JWT access tokens (15 мин) и secure HTTP-only refresh tokens (30 дней). Привязка всех сущностей к `workspace_id` и `user_id`.
    - *AC:* Изоляция арендаторов на уровне запросов, автоматическая инъекция `workspace_id` в ORM-сессию, 401 при истекшем токене, silent refresh.
    - *Оценка:* 5 SP | *Спринт:* S1
  - **FEAT-01-2: User Preferences, Timezones & Locale Engine**
    - *Описание:* Управление профилем, системными темами (light/dark/system), форматами дат, выбором рабочей недели и часовым поясом пользователя (IANA timezone).
    - *AC:* Все даты/время конвертируются в UTC в БД и отображаются в IANA timezone пользователя; валидация локалей (ru/en).
    - *Оценка:* 3 SP | *Спринт:* S1
  - **FEAT-01-3: Multi-Factor Authentication (MFA / TOTP) & Session Management**
    - *Описание:* Подключение TOTP (Google Authenticator), генерация резервных кодов восстановления, принудительный отзыв всех активных сессий (logout all devices).
    - *AC:* RFC 6238 TOTP валидация, rate-limiting на ввод кодов (5 попыток / 15 мин), отзыв refresh tokens при смене пароля или сбросе сессий.
    - *Оценка:* 5 SP | *Спринт:* S2
  - **FEAT-01-4: Today Dashboard Aggregation Engine**
    - *Описание:* Сервисный слой для агрегации данных текущего дня: задачи (due_date = today), события календаря, суточный бюджет и прогресс без создания отдельной таблицы Today в БД.
    - *AC:* Время ответа API агрегации ≤ 100 мс при p95, реактивное обновление при изменении задач/событий, единый payload для веб-клиента.
    - *Оценка:* 5 SP | *Спринт:* S2

#### EPIC-02: Capture & Inbox
- **Приоритет:** P0 | **Спринты:** S3 | **MVP:** Да | **Total SP:** 15
- **Цель:** Реализовать быстрый захват мыслей, задач и расходов из любого контекста системы за ≤ 3 действия без когнитивного трения.
- **Фичи:**
  - **FEAT-02-1: Quick Add Modal & Global Hotkey Framework**
    - *Описание:* Глобальное модальное окно (Cmd/Ctrl+K и мобильный FAB) с автофокусом и real-time preview карточкой сущности.
    - *AC:* Открытие модального окна ≤ 50 мс, создание задачи за 2 действия (ввод текста + Enter), поддержка переключения типов (Task/Event/Expense/Note).
    - *Оценка:* 5 SP | *Спринт:* S3
  - **FEAT-02-2: Rule-based NLP Intent & Entity Extraction**
    - *Описание:* Детерминированный быстрый парсер естественного языка для извлечения дедлайнов ("завтра", "пт", "18:00"), приоритетов (!1..3, !high), проектов (#work) и сумм расходов.
    - *AC:* Время парсинга строки < 15 мс (in-memory regex/rule engine), подсветка распознанных токенов в реальном времени, fallback при неоднозначности.
    - *Оценка:* 5 SP | *Спринт:* S3
  - **FEAT-02-3: Unified Inbox Triage & Assignment**
    - *Описание:* Представление Inbox для неразобранных элементов (без проекта или даты). Быстрые действия в 1 клик для назначения дедлайна, проекта или конвертации типа.
    - *AC:* Badge с точным счетчиком неразобранного (0..99+), drag-and-drop перенос в проект, автоматическое удаление из Inbox после триажа.
    - *Оценка:* 3 SP | *Спринт:* S3
  - **FEAT-02-4: Instant Undo Toast System**
    - *Описание:* Механизм мгновенной отмены последнего действия Quick Add в течение 5 секунд через всплывающий тост.
    - *AC:* Тост активен ровно 5 секунд, нажатие Undo производит мягкое удаление созданного объекта и логирует факт отмены в audit trail.
    - *Оценка:* 2 SP | *Спринт:* S3

#### EPIC-03: Task Management
- **Приоритет:** P0 | **Спринты:** S3–S4 | **MVP:** Да | **Total SP:** 16
- **Цель:** Создать надёжное ядро управления задачами с поддержкой жизненного цикла, иерархии, регулярности и дедлайнов.
- **Фичи:**
  - **FEAT-03-1: Task Core Lifecycle & Metadata Engine**
    - *Описание:* Полный CRUD задач с поддержкой конечного автомата статусов (Inbox -> Todo -> In Progress -> Review -> Done -> Canceled), 4 уровней приоритетов (P1–P4), описания (Markdown) и тегов.
    - *AC:* Валидация недопустимых переходов статусов на уровне домена, optimistic UI updates, автоматическая фиксация `completed_at` при переходе в Done.
    - *Оценка:* 5 SP | *Спринт:* S3
  - **FEAT-03-2: Hierarchical Subtasks & Progress Rollup**
    - *Описание:* Древовидная структура подзадач (до 2 уровней вложенности в MVP) с автоматическим пересчетом процента выполнения родительской задачи.
    - *AC:* Завершение всех подзадач предлагает завершить родительскую задачу, удаление родительской задачи каскадно удаляет подзадачи (soft delete).
    - *Оценка:* 3 SP | *Спринт:* S4
  - **FEAT-03-3: Recurring Tasks Engine (RRULE Engine)**
    - *Описание:* Генератор повторяющихся задач по паттернам (ежедневно, по рабочим дням, еженедельно, ежемесячно) с вычислением следующего инстанса только при закрытии текущего.
    - *AC:* Строгое соблюдение инварианта "один активный инстанс на серию", поддержка сохранения истории прошлых выполнений, сохранение таймзоны серии.
    - *Оценка:* 5 SP | *Спринт:* S4
  - **FEAT-03-4: Overdue & Deadline Computation Engine**
    - *Описание:* Вычисляемый статус просрочки (computed field `is_overdue`, не сохраняемый статически в БД), сравнение с текущим моментом в таймзоне пользователя.
    - *AC:* Динамический фильтр просроченных задач, автоматическая группировка в Today Dashboard, отсутствие рассинхронизации статуса в базе.
    - *Оценка:* 3 SP | *Спринт:* S4

- **Цель:** Обеспечить структурирование задач по проектам с гибким управлением статусами, визуальной дифференциацией и архивацией.
- **Фичи:**
  - **FEAT-04-1: Project Hierarchy, Colors & Metadata**
    - *Описание:* Создание проектов с цветовым кодированием, иконками, описанием, дедлайнами и назначением владельца.
    - *AC:* Уникальность имени проекта внутри рабочего пространства, палитра цветов доступности, валидация прав доступа.

    - *Описание:* Определение контрольных точек (вех) проекта и автоматический расчет общего прогресса на основе статусов связанных задач.
    - *AC:* Прогресс-бар на карточке проекта (completed_tasks / total_tasks * 100%), расчет ожидаемой даты завершения.

    - *AC:* Защита от случайного удаления активных задач (confirm modal с вводом имени), возможность восстановления проекта из архива без потери структуры.

#### EPIC-05: Kanban
- **Приоритет:** P0 | **Спринты:** S4 | **MVP:** Да | **Total SP:** 13
- **Цель:** Предоставить пользователю визуальное представление задач на виртуализированной доске без дублирования сущностей в базе данных.
- **Фичи:**
  - **FEAT-05-1: Virtualized Kanban Board over Task State**
    - *Описание:* Интерактивная доска, колонки которой отображают задачи по их `Task.status`. Отсутствие отдельной таблицы `kanban_cards` — доска является проекцией домена Tasks.
    - *AC:* Отрисовка до 500 карточек без лагов (FPS ≥ 55) за счет виртуализации колонок, мгновенная фильтрация по проектам и тегам.
    - *Оценка:* 5 SP | *Спринт:* S4
  - **FEAT-05-2: Drag-and-Drop Task Transitions & Fractional Ordering**
    - *Описание:* Перетаскивание карточек между колонками со смене статуса задачи и упорядочиванием внутри колонки с использованием дробных индексов (lexicographical / fractional indexing).
    - *AC:* Drag-and-drop переводит статус задачи и отправляет PATCH-запрос с optimistic UI; дробный индекс исключает массовый перезапуск порядка всей колонки.
    - *Оценка:* 5 SP | *Спринт:* S4
  - **FEAT-05-3: Kanban Swimlanes & Multi-Criteria Filtering**
    - *Описание:* Горизонтальные дорожки (swimlanes) по проектам или приоритетам, а также комплексный фильтр (срок, ответственный, метка).
    - *AC:* Сохранение состояния открытых свимлейнов в localStorage, мгновенная перерисовка при переключении фильтров.
    - *Оценка:* 3 SP | *Спринт:* S4

#### EPIC-06: Calendar
- **Приоритет:** P0 | **Спринты:** S6 | **MVP:** Да | **Total SP:** 15
- **Цель:** Реализовать нативный тайм-менеджмент с расписанием событий, просмотром сетки времени и планированием задач во временных слотах.
- **Фичи:**
  - **FEAT-06-1: Multi-View Native Calendar Engine**
    - *Описание:* Интерактивный календарь с поддержкой представлений День, Неделя, Месяц и Повестка дня (Agenda) с шагом сетки 15/30/60 минут.
    - *AC:* Плавный скролл, позиционирование текущего времени (красная линия индикатора), корректная обработка перехода через полночь и переход на летнее/зимнее время.
    - *Оценка:* 5 SP | *Спринт:* S6
  - **FEAT-06-2: Task Time Blocking Engine**
    - *Описание:* Возможность перетащить задачу из боковой панели задач в календарный слот, превратив её во временной блок (Time Block) с фиксированной длительностью.
    - *AC:* Создание двусторонней связки между `Task` и `CalendarEvent`; изменение времени в календаре обновляет дедлайн/время задачи; удаление блока не удаляет задачу.
    - *Оценка:* 5 SP | *Спринт:* S6
  - **FEAT-06-3: Event Conflict Detection & Recurrence Handling**
    - *Описание:* Обнаружение пересечений событий и визуальное предупреждение пользователя при наложении встреч, а также поддержка повторяющихся событий (iCalendar RFC 5545).
    - *AC:* Визуальный бейдж конфликта в UI, предупреждение при сохранении, генератор инстансов серии без взрыва базы данных.
    - *Оценка:* 5 SP | *Спринт:* S6

#### EPIC-07: Google Calendar Integration
- **Приоритет:** P0 | **Спринты:** S7–S8 | **MVP:** Да | **Total SP:** 18
- **Цель:** Обеспечить надежную двухстороннюю синхронизацию событий между Personal OS и Google Calendar с детерминированным разрешением конфликтов.
- **Фичи:**
  - **FEAT-07-1: Google OAuth2 Consent & Encrypted Token Vault**
    - *Описание:* Подключение Google Calendar через OAuth2 с scope `calendar.events`, безопасное шифрование refresh token (AES-256-GCM) в базе данных и автообновление access tokens.
    - *AC:* Токены хранятся только в зашифрованном виде; автоматический silent refresh токена за 5 минут до экспирации; статус подключения в профиле.
    - *Оценка:* 3 SP | *Спринт:* S7
  - **FEAT-07-2: Outbound Event Sync Pipeline (Personal OS -> Google)**
    - *Описание:* Асинхронная отправка созданных/измененных/удаленных событий из Personal OS в Google Calendar через очередь Celery с идемпотентными ключами.
    - *AC:* Задержка отправки в Google < 5 сек, retry с экспоненциальной задержкой (exponential backoff) при ошибках сети или 429 от Google API.
    - *Оценка:* 5 SP | *Спринт:* S7
  - **FEAT-07-3: Inbound Webhook Receiver & Push Notifications (Google -> Personal OS)**
    - *Описание:* Прием входящих webhook-уведомлений от Google push-каналов, валидация заголовков канала (`X-Goog-Channel-Token`), инкрементальная синхронизация измененных событий.
    - *AC:* Ответ 200 OK вебхуку Google за ≤ 200 мс с помещением обработки в Celery; корректная обработка продления жизни подписки на канал.
    - *Оценка:* 5 SP | *Спринт:* S8
  - **FEAT-07-4: Conflict Resolution Engine & Sync Replay Test Suite**
    - *Описание:* Детерминированное разрешение конфликтов одновременного редактирования по правилу "Personal OS wins", защита от бесконечных циклов синхронизации (loopback suppression).
    - *AC:* Однозначное исключение дубликатов с помощью таблицы внешних маппингов (`gcal_event_id` <-> `internal_id`), успешное прохождение реплей-тестов с имитацией гонок.
    - *Оценка:* 5 SP | *Спринт:* S8

#### EPIC-08: Finance

    - *AC:* Полное отсутствие ошибок округления чисел с плавающей точкой (float forbidden); баланс счета пересчитывается транзакционно с блокировкой строк (FOR UPDATE).
    - *Оценка:* 5 SP | *Спринт:* S9
  - **FEAT-08-2: Income/Expense Transactions & Category Taxonomy**
    - *Описание:* Учет операций расходов, доходов и переводов между счетами. Иерархическое дерево категорий расходов и доходов с системными пресетами.
    - *AC:* Поддержка переводов между счетами с фиксацией курса, прикрепление чеков/заметок, запрет удаления категории при наличии привязанных транзакций.
    - *Оценка:* 5 SP | *Спринт:* S9
  - **FEAT-08-3: Monthly & Category Budget Limits with Proactive Alerts**
    - *Описание:* Установка лимитов расходов на месяц и по категориям. Мониторинг процента расхода бюджета с генерацией предупреждений при достижении 80% и 100%.
    - *AC:* Автоматический расчет остатка дневного бюджета ("Safe to spend today"); отправка уведомления при превышении порога в течение 1 минуты.
    - *Оценка:* 5 SP | *Спринт:* S10
  - **FEAT-08-4: Financial Analytics Dashboard & Trend Visualization**
    - *Описание:* Аналитический дашборд: график Cashflow (доходы vs расходы), круговая диаграмма распределения трат по категориям, динамика накоплений и экспорт в CSV.
    - *AC:* Рендеринг аналитических отчетов за период до 1 года < 300 мс; экспорт валидного CSV файла с соблюдением кодировки UTF-8 BOM.
    - *Оценка:* 5 SP | *Спринт:* S10

## 4. DEFINITION OF DONE (DOD)

Каждая пользовательская история (User Story) и фича (Feature) считаются завершенными (Done) и готовыми к поставке на Staging/Production только при 100% выполнении следующего чеклиста:

```
[ ] Domain invariant tests pass
[ ] REST contract documented
[ ] Authorization enforced
[ ] Tenant isolation tested
[ ] Idempotency decision made
[ ] Telemetry present
[ ] E2E critical path passes
```

### Развернутые требования к критериям DoD:

1. **Domain Invariant Tests Pass:**
   - Все бизнес-правила домена покрыты модульными тестами (unit tests).
   - Финансовые балансы проверяются на отсутствие отрицательных единиц и равенство сумме транзакций.
   - Задачи валидируют граф статусов (нельзя прыгнуть из Inbox в Done в обход правил валидации).
   - Денежные суммы хранятся строго в целых минорных единицах (`INTEGER`), float запрещен.
   - Code coverage модульными тестами по домену ≥ 80%.

2. **REST Contract Documented:**
   - Эндпоинт полностью описан в OpenAPI 3.1 схеме (FastAPI Swagger / Redoc).
   - Все Request Body и Response Body типизированы строгими Pydantic v2 моделями.
   - Описаны коды ответов: 200/201 (успех), 400 (ошибка валидации), 401 (не авторизован), 403 (доступ запрещен), 404 (не найдено), 409 (конфликт), 422 (семантическая ошибка).
   - Примеры запросов и ответов включены в контракт.

3. **Authorization Enforced:**
   - Каждый входящий запрос проверяется на валидность JWT Bearer токена.
   - Реализована проверка ролей и прав доступа (RBAC / Owner permissions).
   - Неавторизованные запросы немедленно отклоняются со статусом 401 Unauthorized до выполнения логики контроллера.

4. **Tenant Isolation Tested:**
   - В каждой таблице базы данных присутствует колонка `workspace_id`.
   - Запросы к БД фильтруются по `workspace_id` текущей сессии на уровне ORM / Repository.
   - Написан обязательный негативный интеграционный тест: попытка доступа пользователя A к сущности пользователя B возвращает строго 404 Not Found (не 403, во избежание сканирования ID).

5. **Idempotency Decision Made:**
   - Для всех мутирующих операций (POST / PUT / PATCH / DELETE) принято и задокументировано явное решение по идемпотентности.
   - Критические операции (создание транзакции, списание, генерация инстанса повторяющейся задачи, вебхук Telegram, синхронизация Google) поддерживают заголовок `Idempotency-Key`.
   - Повторный запрос с тем же ключом возвращает закешированный результат без повторного выполнения бизнес-логики.

6. **Telemetry Present:**
   - Эндпоинт обернут в спан OpenTelemetry с сохранением `trace_id` и семантических атрибутов.
   - Экспортируются стандартные RED метрики Prometheus: частота запросов, latency histogram, счетчик ошибок.
   - Все ошибки логируются в формате Structured JSON со ссылкой на `request_id`, `user_id`, `workspace_id` и отправляются в Sentry.
   - В логах отсутствуют конфиденциальные данные (пароли, токены, реквизиты карт).

7. **E2E Critical Path Passes:**
   - Критические пользовательские сценарии автоматизированы в Playwright E2E тестах.
   - Тесты проверяют сквозной путь в реальном браузере: рендеринг UI -> API -> БД -> обратная связь пользователю.
   - Все E2E тесты стабильно проходят в GitHub Actions CI пайплайне без флапающих падений (flaky tests).

## FINDINGS

1. **Единое ядро вместо разрозненных сервисов:**
   Архитектурный принцип "одно ядро — разные проекции" подтвердил свою состоятельность. Kanban (EPIC-05), Today Dashboard (EPIC-01/FEAT-01-4) и Telegram Bot (EPIC-10) не требуют отдельных таблиц карточек или сообщений — они оперируют напрямую доменными сущностями Task, Event, Transaction через единый API.
2. **Синхронизация Google Calendar — ключевая точка риска:**
   Двусторонняя синхронизация (EPIC-07) несет риск бесконечных циклов и гонок правок. Принятое решение "Personal OS wins" при конфликтах и внедрение идемпотентных ключей с подавлением обратной связи (loopback suppression) снимает этот риск.
3. **Безопасность AI через Policy Engine:**
   AI Advisor (EPIC-12) ни при каких условиях не должен напрямую мутировать базу данных. Схема "AI предлагает Diff -> Human подтверждает в 1 клик -> Ядро применяет" полностью защищает от галлюцинаций и непреднамеренного повреждения данных.
4. **Финансовая строгость:**
   Хранение валюты в `INTEGER` (минорные единицы) и детерминированный пересчет баланса счета предотвращают накопление ошибок округления и обеспечивают соответствие финтех-стандартам.
